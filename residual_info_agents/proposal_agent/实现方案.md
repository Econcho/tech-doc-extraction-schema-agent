proposal agent代码实现方案

## 1. 总体落地边界

在现有 `residual_info_agents` 下新增 `proposal_agent` 及其配套模块。Proposal Agent 不直接处理全部 residual block，而是消费 Triage Agent 产出的 `new_schema / new_attr` 结论，将其转化为 `TriageSignal`，通过 embedding 召回和 bucket routing 聚合同类信号；当 bucket 满足触发条件后，再进入 Proposal Agent Loop 生成 proposal，并由 ProposalCheck SubAgent 检查与现有 schema 的重复和边界冲突。

设计文档中已经定义了 Proposal 阶段的核心对象：`TriageSignal` 是向量召回和 bucket routing 的标准化信号对象；`Bucket` 是外部维护的候选 proposal 聚合容器，不是向量数据库内部对象，也不是 proposal 本体；Bucket 类型包括 `new_schema / new_attr`，状态包括 `incubating / stable / stale / ambiguous / split / merged / archived / rejected`。

## 3. `domain/proposal` 数据结构设计

### 3.1 `enums.py`

定义 Proposal 阶段所有枚举。

内容包括：

```text
BucketProposalType

- new_attr

BucketStatus
- incubating
- stable
- stale
- ambiguous
- split
- merged
- archived
- rejected

SignalBucketMappingStatus
- active
- removed
- remapped
- merged
- rejected

ProposalStatus
- draft
- checked
- conflict
- accepted
- rejected
- needs_revision
```

设计文档中已经给出 Bucket 类型和 BucketStatus 的主要枚举，直接落到代码即可。

---

### 3.2 `signal.py`

定义 `TriageSignal` 与 `SignalInfoRuntimeBlock`。

`TriageSignal` 是存储和 routing 用对象：

```text
TriageSignal
- signal_id: str
- doc_ref: str
- extraction_doc_ref: str | None
- block_id: int
- heading_tree: list[str]
- text: str
- reason: str
- conclusion: new_schema | new_attr
- related_old_schema_name: str
- confidence: float
- source_embedding_text: str
- reason_embedding_text: str
- created_at: str
```

其中：

```text
source_embedding_text = heading_tree + resblock_text
reason_embedding_text = triage_reason
```

设计文档里同时出现过 `embedding_text=heading_tree + resblock_text + triage_reason` 和双索引策略 `source_index = heading_tree + resblock_text / reason_index = triage_reason`。落地时建议采用双字段，避免把 reason 强行混入原文语义。

`SignalInfoRuntimeBlock` 是 ProposalAgent runtime 输入对象：

```text
SignalInfoRuntimeBlock
- doc_ref: str
- extraction_doc_ref: str | None
- resblock_id: int
- heading_tree: list[str]
- text: str
```

注意：runtime block 不放 `reason`。设计文档已经说明原因：reason 是 TriageAgent 对 residual 的一次加工结果，ProposalAgent 本身也具备产生 reason 的能力，直接输入 reason 可能干扰大于作用。

```text
- lineage: BucketLineage | None

- updated_at: str
```

`BucketLineage`：

```text
BucketLineage
- parent_bucket_ids: list[str]

- split_from: str | None
- operation_reason: str
```

这部分对应设计文档里 `Bucket`、`BucketLineage` 和 `member_signal_ids / support_doc_count / support_signal_count` 的定义。

### 3.4 `mapping.py`

定义 signal 到 bucket 的映射。

```text
SignalBucketMapping
- signal_id: str
- bucket_id: str

- route_reason: str | None
```

设计文档中已定义 `SignalBucketMapping: signal_id / bucket_id / status / assigned_at`，代码可加 `score / route_reason` 作为调试字段，但如果你想严格贴合文档，MVP 可以先不加。

### 3.5 `runtime.py`

定义 Proposal Agent 的工作上下文。

```text
ProposalWorkingContext
- bucket_id: str
- bucket_type: new_schema | new_attr
- schema_description: str
- signals: list[SignalInfoRuntimeBlock]
- bucket_metadata: Bucket
- tool_results: list[ToolResult]
- turn_count: int
```

`LoopState`：

```text
ProposalLoopState
- context: ProposalWorkingContext
- turn_count: int
- transition_reason: str
```

设计文档中 `WorkContext` 至少包括 `bucket_id` 和 `signals`，`LoopState` 包括 `context / turn_count / transition_reason`。这里是在不改变核心定义的前提下补足 schema 和 tool result，用于真正跑 LLM loop。

### 3.6 `proposal.py`

定义 Proposal Agent 最终输出对象。

MVP 必须补这个，否则 Proposal Agent 没有落盘对象。

```text
ProposalDraft
- proposal_id: str
- bucket_id: str
- proposal_type: new_schema | new_attr
- proposed_name: str
- definition: str
- motivation: str
- related_old_schema_name: str
- supporting_signal_ids: list[str]
- representative_examples: list[str]
- attributes: list[ProposedAttribute]
- confidence: float
- risk_flags: list[str]
- created_at: str
```

`ProposedAttribute`：

```text
ProposedAttribute
- name: str
- description: str
- value_type: str
- required: bool
```

`ProposalCheckResult`：

```text
ProposalCheckResult
- proposal_id: str
- bucket_id: str
- passed: bool
- conflict_type: none | duplicate | overlap | wrong_granularity | attribute_should_belong_to_existing_schema | too_broad | too_narrow | insufficient_support
- conflicting_schema_names: list[str]
- reason: str
- suggested_action: accept | revise | reject | request_more_evidence
```

设计文档只说 `ProposalCheck-SubAgent` 检查 ProposalAgent 输出是否和现有 schema 存在边界冲突。落地时必须将这个检查结果结构化，否则无法工程化消费。

## 4. `proposal_pipeline`：从 TriageResult 到 Bucket

### 4.1 `triage_result_loader.py`

职责：

```text
读取 triage_agent 输出目录中的 conclusion.json / jsonl
筛选 conclusion in ["new_schema", "new_attr"]
忽略 noise / existing_schema_covered / uncertain
返回 TriageConclusion 列表
```

建议输入来源：

```text
residual_info_agents/triage_agent/.conclusions/conclusion.json
```

但目录名建议先修正为：

```text
.conclusions/
```

---

### 4.2 `signal_builder.py`

职责：

```text
TriageConclusion + ResidualBlock → TriageSignal
```

输入：

```text
triage conclusion
residual_info json
original_doc_ref
extraction_doc_ref
```

输出：

```text
TriageSignal
```

核心规则：

```text
signal.type = conclusion
signal.reason = triage conclusion reason
signal.source_embedding_text = "\n".join(heading_tree) + "\n" + text
signal.reason_embedding_text = reason
```

注意：`reason` 用于 embedding 的 reason_index，但不进入 ProposalAgent runtime 的 `SignalInfoRuntimeBlock`。

---

### 4.3 `signal_ingestion.py`

职责：

```text
将 TriageSignal 写入 signal_store
调用 embedding_client 生成 source embedding / reason embedding
写入 vector_store 的 source_index / reason_index
调用 bucket_router 给 signal 分配 bucket
更新 Bucket / SignalBucketMapping
触发 BucketMonitor 判断是否 allow proposal
```

对应设计文档里的存储 workflow：TriageResult 转 TriageSignal，经 source embedding 和 reason embedding 分别进入向量库，TopK 后经 bucket rank / rerank 选择 Top1 bucket，满足阈值则 join，否则创建新 bucket。

---

### 4.4 `bucket_merge_checker.py`

职责：

```text
当 top1 bucket 与 top2 bucket 的分数接近时，触发 merge 检查
满足 merge 条件时创建新 bucket
更新 lineage
将旧 bucket 标记为 merged
更新 mapping
```

设计文档中 merge 触发条件是 bucket rank 中 rank1 与 rank2 权重差小于 alpha 时进行检查；merge 流程是创建新 bucket，signal 为 A + B。

落地建议：MVP 先实现 `mark_to_be_merged` 或直接 `merge` 二选一。为了减少复杂度，MVP 可以先只记录 merge candidate，不自动合并。

---

### 4.5 `proposal_trigger.py`

职责：

```text
判断 bucket 是否 allow proposal
```

判断时机：

```text
1. 每次 Bucket append new signal 后，对该 bucket 判断
2. DB 每新增 N 个 signal，对长期无新增的 bucket 判断
```

判断条件：

```text
support_doc_count > M
support_signal_count > N
```

设计文档中 allow proposal 判断时机与条件已经给出，可直接落地。

---

## 5. `proposal_embedding`：embedding、向量库、bucket routing

### 5.1 `embedding_client.py`

职责：

```text
统一 embedding 接口
当前 MVP 可先支持本地 bge-m3
后续可扩展 text-embedding-3-small / large
```

接口：

```text
embed_texts(texts: list[str]) -> list[list[float]]
```

配置项：

```text
provider: bge_m3 | openai
model_name
batch_size
device
```

设计文档中建议 MVP 先选 `bge-m3`，云服务成本优先用 `text-embedding-3-small`，质量上限用 `text-embedding-3-large`，最终通过 bucket route accuracy、bucket purity、proposal acceptance rate 做模型选择。

---

### 5.2 `vector_store.py`

职责：

```text
维护 source_index 和 reason_index
支持 add_signal
支持 search_topk
```

MVP 方案：

```text
JSONL + numpy/faiss 本地索引
```

接口：

```text
add(signal_id, bucket_id, vector, index_name)
search(vector, top_k, index_name) -> list[VectorHit]
```

`VectorHit`：

```text
signal_id
bucket_id
similarity
rank
index_name
```

---

### 5.3 `bucket_ranker.py`

职责：

```text
TopK hits → bucket score
```

输入：

```text
topk_hits: list[VectorHit]
```

输出：

```text
list[BucketRankResult]
```

`BucketRankResult`：

```text
bucket_id
score
support_hit_count
high_support_count
low_penalty_count
member_hit_ids
```

实现原则来自设计文档：

```text
topK 中有更多高相似度向量的桶更靠前
低相似度向量更多的桶更靠后
极少数极高相似度不应压过大量较高相似度
```

计算使用文档中的 `N_eff` 与 score 公式，MVP 可以把公式参数放入 `config.yaml`：

```text
tau_high
tau_low
alpha
epsilon
```

设计文档第 5 页给出了 bucket rank 原则与有效支持数 `N_eff` 的计算动机。

---

### 5.4 `bucket_router.py`

职责：

```text
对新 TriageSignal 进行 bucket routing
```

流程：

```text
1. 用 source_embedding_text 查 source_index TopK
2. 用 reason_embedding_text 查 reason_index TopK
3. RRF 合并两个 index 的结果
4. 调 bucket_ranker 得到 bucket rank
5. 如果 Top1 score > threshold，join Top1 bucket
6. 否则 create new bucket
7. 如果 Top1 - Top2 < alpha，触发 merge_check
```

设计文档中写了 source_index、reason_index、RRF rerank、Top1 bucket / create new bucket、Top1-Top2 小于 alpha 触发 merge 检查。

---

### 5.5 `bucket_monitor.py`

职责：

```text
监控 bucket 状态
判断 allow proposal
触发 ProposalAgent
```

接口：

```text
on_bucket_appended(bucket_id)
on_signal_db_growth()
get_allow_proposal_buckets()
```

## 7. `proposal_agent/proposal_agent.py`

### 7.1 类定位

`ProposalAgent` 复用你已经形成的 harness 思想：

```text
WorkingContext + ToolHandler + LLM + Loop
```

但它的输入不是 `schema + resinfojson`，而是：

```text
schema_description + bucket_id
```

它通过 bucket_id 找到 bucket 内 signals，并构造 ProposalWorkingContext。

---

### 7.2 最小 public 方法

```text
build_context(bucket_id, schema_description)
main_loop(bucket_id, schema_description)
```

---

### 7.3 `build_context`

职责：

```text
读取 Bucket
读取 member_signal_ids
读取对应 TriageSignal
转换为 SignalInfoRuntimeBlock，不带 reason
构造 ProposalWorkingContext
```

注意：ProposalAgent runtime 不输入 reason，这一点与设计文档一致。

---

### 7.4 `main_loop`

流程：

```text
1. build_context(bucket_id, schema_description)
2. 构造 system prompt = ProposalAgentSkill.md
3. user message = ProposalWorkingContext JSON
4. LLM 判断 evidence 是否足够
5. 证据不足：调用 evidence tools
6. 证据足够：输出 ProposalDraft JSON
7. ProposalDraft 落盘
8. 调 ProposalCheckSubAgent
9. ProposalCheckResult 落盘
10. 若 passed，状态置 checked / stable；若 conflict，置 conflict / needs_revision
```

Proposal workflow 图中包含 WorkingContext、Task Description、Schema Description、LLM、Tool Call、Evidence、ToolHandler、Proposal、ProposalCheck SubAgent，代码组织应按这个 loop 落地。

---

### 7.5 ProposalAgent 输出 contract

`ProposalAgentSkill.md` 中要求输出：

```text
{
  "proposal": {
    "proposal_type": "new_schema | new_attr",
    "proposed_name": "...",
    "definition": "...",
    "motivation": "...",
    "related_old_schema_name": "...",
    "supporting_signal_ids": [...],
    "representative_examples": [...],
    "attributes": [...],
    "confidence": 0.0,
    "risk_flags": [...]
  }
}
```

如果证据不足，允许 native tool call。

如果 bucket 混杂，允许输出：

```text
{
  "action": "split_required",
  "reason": "...",
  "suggested_groups": [...]
}
```

MVP 如果不做 split，可以先把 `split_required` 落为 `BucketStatus.ambiguous`，人工处理。

## 8. `proposal_agent/proposal_check_agent.py`

### 8.1 类定位

`ProposalCheckSubAgent` 不生成 proposal，只检查边界冲突。

输入：

```text
schema_description
ProposalDraft
supporting signals
```

输出：

```text
ProposalCheckResult
```

---

### 8.2 检查维度

```text
duplicate：是否与现有 schema 重复
overlap：是否边界重叠
wrong_granularity：粒度是否过粗或过细
attribute_should_belong_to_existing_schema：是否应作为旧 schema 属性
too_broad：定义过宽
too_narrow：定义过窄
insufficient_support：证据不足
```

设计文档只要求检查与现有 schema 的边界冲突，以上是落地所需的最小结构化拆解。

---

## 9. `proposal_agent/TOOLS.json`

ProposalAgent 可以复用 TriageAgent 的三个 evidence tools：

```text
get_neighbor_text_of_resblocks
get_extraction_result_of_neighbor_text
get_original_text_from_heading_tree
```

设计文档中 Proposal 阶段 tools 与 Triage 阶段一致，分别返回 ContextBlock、NeighborExtractions、FullHeadingContext。

与 Triage 不同的是：工具输入里的 `resblock_ids` 来自 bucket signals，而不是 active_resblocks。

## 11. 主流程落地顺序

### Phase 1：只做信号入库和 bucket routing

新增命令：

```text
python -m residual_info_agents.proposal_pipeline.ingest_triage_results
```

流程：

```text
triage conclusions
→ filter new_schema/new_attr
→ build TriageSignal
→ embedding
→ vector_store.add
→ bucket_router.route
→ bucket_store update
→ mapping_store append
```

产物：

```text
proposal_signals.jsonl
proposal_buckets.json
signal_bucket_mappings.jsonl
```

---

### Phase 2：实现 BucketMonitor

新增命令：

```text
python -m residual_info_agents.proposal_pipeline.scan_allow_proposal
```

流程：

```text
遍历 buckets
检查 support_doc_count / support_signal_count
满足条件则 status = stable 或 allow_proposal
输出 allow_proposal_buckets
```

---

### Phase 3：实现 ProposalAgent Loop

新增命令：

```text
python -m residual_info_agents.proposal_agent.run --bucket_id xxx
```

流程：

```text
bucket_id
→ ProposalWorkingContext
→ LLM + tools
→ ProposalDraft
→ ProposalCheckSubAgent
→ ProposalCheckResult
→ 落盘
```

---

### Phase 4：补 merge / split

MVP 后再做：

```text
bucket_merge_checker
split_required handling
ambiguous bucket review
```

不要一开始同时实现 merge/split/proposal/check，否则容易把主链路复杂化。

## 13. MVP 最小完成标准

Proposal Agent MVP 达标条件：

```text
1. 能从 triage conclusion 中筛出 new_schema / new_attr
2. 能生成 TriageSignal
3. 能写入 source_index / reason_index
4. 能基于 TopK + bucket rank 分配 bucket
5. 能维护 Bucket / SignalBucketMapping
6. 能判断 allow proposal
7. 能针对一个 bucket 构造 ProposalWorkingContext
8. 能让 ProposalAgent 输出 ProposalDraft
9. 能让 ProposalCheckSubAgent 输出 ProposalCheckResult
10. 所有产物可落盘复盘
```

暂不强制：

```text
1. 自动 merge
2. 自动 split
3. proposal 自动写回 schema
```
